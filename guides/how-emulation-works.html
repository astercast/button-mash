How emulation works

Your browser can pretend to be a Game Boy Advance. Not approximately — precisely enough that games can't tell the difference. Here's the trick, without the jargon.

  • ⏱ ~8 min
  • Beginner
Legal lane: emulators are software — legal, and mostly open-source. The games you load into them must be yours: your own dumps, homebrew, or public domain. The full rules.

The core idea: a convincing forgery

A game is just machine code — a list of instructions for a specific chip. An emulator is a program that pretends to be that chip, plus all the other chips around it (graphics, sound, timers), well enough that the game never notices it's not on real hardware. Every frame, the emulator runs the game's code, draws what the graphics chip would have drawn, plays what the sound chip would have played, and checks your keyboard as if it were a controller.

That's it. That's emulation. Everything else is engineering to make the forgery faster and more exact.

Interpreters vs. recompilers

There are two ways to run foreign machine code:

  • Interpretation — read one instruction, simulate it, repeat. Simple, accurate, and slow: every game instruction costs many host instructions. Most emulators start here, and many stay here — modern hardware is fast enough that interpretation works fine up through the 16-bit era and beyond.
  • Recompilation — translate whole chunks of game code into the host's native language ahead of time (or just-in-time), then run the translation directly. Much faster, much more complex to get right. This is how your browser runs a PlayStation game at full speed, and it's the pattern behind the GBA-to-WASM projects.

Think of it as the difference between a UN interpreter translating speech live (interpretation) and publishing a translated book (recompilation).

Why "cycle accuracy" matters

Old games don't just run code — they race the hardware. A SNES game might change the background color at the exact moment the TV beam reaches a certain scanline. If your emulator runs the CPU slightly too fast or too slow relative to the graphics chip, the effect breaks: flicker, wrong colors, glitched sprites.

Cycle accuracy means simulating the chips in lockstep, counting every clock tick the way real silicon does. It's expensive — a cycle-accurate SNES emulator needs far more horsepower than a rough one — but it's why some emulators play every game flawlessly while others have a compatibility list full of asterisks.

What a BIOS actually does

Some consoles boot through built-in firmware — the BIOS — which initializes hardware and provides helper routines games call into. Emulators handle this three ways:

  • Require the real BIOS (PlayStation, Sega CD): you dump it from your own hardware. No download, ever.
  • Reimplement it (GBA via mGBA): clean-room code that behaves the same way. No file needed.
  • Don't need one (NES, SNES, Genesis): the console had no meaningful BIOS to begin with.

Save states: the superpower real hardware never had

A save state is a complete snapshot of the emulated machine — every register, every byte of RAM, the exact position of the graphics beam. Freeze it, restore it instantly. It's why emulators feel magical: you can save mid-jump. In the browser, states live in local storage or IndexedDB, which is why the Player remembers your progress between visits.

Why the browser is enough now

Three things converged: WebAssembly runs compiled emulator cores at near-native speed; Web Audio and Canvas/WebGL handle sound and graphics with low latency; and modern laptops are simply thousands of times faster than a 2001 handheld. The result: a GBA emulator in a tab, no install, full speed. That's what powers this site's Player and Converter.
