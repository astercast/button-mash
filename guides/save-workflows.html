Saves that survive

States, SRAM, and memory cards are three different machines wearing the same trench coat. Learn what each one is, where it actually lives, and the backup routine that outlives dead batteries and browser wipes.

  • Covers: RetroArch + this site's Player
  • ⏱ ~12 min
  • Beginner

01The three save machines

Save states
A complete snapshot of the emulated machine — CPU, RAM, graphics chips, everything — frozen mid-frame. Save mid-jump, reload exactly there. Invented by emulators; no original hardware ever had this.
Battery saves (SRAM)
The game's own save system: the cartridge's battery-backed RAM chip, faithfully emulated. When the game says "saving… do not turn off the power," this is what's being written. Works on real hardware too.
Memory cards / controller paks
Disc-era external storage: the PlayStation's memory card, the N64's Controller Pak. Emulators store these as card image files — virtual plastic you can copy like any file.

The one-sentence version: states are the emulator's snapshots, SRAM is the game's diary, cards are the game's filing cabinet. Each needs a different backup habit.

02Save states: snapshots of everything

States are the most powerful and the most fragile save type. Powerful because they capture everything — reload a state and the game continues as if no time passed, mid-boss-fight or mid-cutscene. Fragile for two reasons:

  • They're version-tied. A state file records the emulator's internal layout, so a state saved in one emulator version (or one core) usually won't load in another. Update your emulator, and old states may simply refuse.
  • They're all-or-nothing. A corrupted state is a dead save — there's no "load the backup slot inside the state."

The discipline: use states for convenience, SRAM for permanence. States for the tricky jump and the boss door; the game's own save for the 40-hour file. And export important states as files before any emulator update — an exported .state file in a folder you back up beats a state living only in a browser's IndexedDB.

Rule of thumb: if losing it would make you quit the game, it should exist as both a state file and an in-game save, in two places. Redundancy is the whole game.

03Battery saves: the game's own memory

On original cartridges, your save lived on an SRAM chip kept alive by a tiny battery — which is why thirty-year-old carts with dead batteries greet you with an empty save screen. Emulators replicate the SRAM chip as a file (often .srm), written when the game saves and flushed to disk when you close the game.

Two things worth knowing:

  • SRAM is portable. The raw bytes are the game's own format, so an .srm usually moves between emulators, between emulator and flash cart, even between your phone and your PC. It's the closest thing to a universal save format retro gaming has.
  • Close cleanly. Some emulators only write the SRAM file when the game closes properly. Yanking the window shut can cost you the last save. Use the emulator's quit/close-content path, or enable periodic SRAM autosave if your emulator offers it.

If you're dumping your own cartridges (see the rip-your-own guide), dump the SRAM too — most USB dumpers back up save RAM, and that 100-hour file is irreplaceable in a way the ROM isn't.

04Memory cards & controller paks

Disc-era consoles moved saves off the game media and onto cards you owned. Emulators keep the metaphor: a memory card image is a file (commonly .mcr for PlayStation) that behaves exactly like the plastic card — 15 blocks, copy/delete in the console's BIOS menu, the works.

  • One card per game vs. one card for everything: emulators let you choose. Per-game cards keep saves organized and avoid the classic "card full" tragedy; a shared card is nostalgic but fragile.
  • Back up the card file. It's a single file — copy it with the 3-2-1 routine in section 8 and your entire PS1 library's progress is safe.
  • N64 Controller Paks work the same way (often .mpk or .n64 files) — and note the original hardware's paks also had batteries that die.

05Where RetroArch keeps it all

RetroArch centralizes saves under its save directories (configurable in Settings → Directory):

  • Savefiles — SRAM and memory-card images land here, named after the game. This is the folder to back up.
  • Savestates — state files with numbered slots per game. Quick Menu → Save State writes here.
  • SaveRAM autosave interval — in Settings → Saving, you can make RetroArch flush SRAM to disk every N seconds instead of only on close. Turn it on; it costs nothing and has saved more files than any other single setting.
  • State slot hotkeys — set these. Fumbling through menus mid-boss-fight is how states get saved over.

RetroArch's per-game remap and override files live nearby — back up the whole config directory and a fresh install restores in minutes. (Setup from scratch? The RetroArch setup guide walks it.)

06Where this site's Player keeps it all

Our Player runs the EmulatorJS engine, and its save model has two modes — knowing which you're in matters:

Default mode: states download as files
The engine's 4.2.3 stable build downloads save states as raw .state files (named after the game file) when you save in-game. They're already files — put them somewhere safe.
Keep in Browser mode: states live in IndexedDB
Switch the engine to Keep in Browser (in-game menu → Settings → Save States) and states are stored in the browser's IndexedDB (EmulatorJS-states store, keyed <game>.state). This unlocks the Player's Save tool: named slots per game (save / restore / rename / export / delete), optional auto-save every 1, 5, or 15 minutes, and one-click export of any state to a file.

The Player's panels work off the most recent game even before a fresh boot, and cheats/remaps/display settings live in the same browser storage keyed per game and per system. Browser storage is convenient but mortal — clearing site data wipes it. Export anything you care about. A downloaded .state file in your documents folder survives what a browser wipe doesn't.

07Moving saves between emulators

  • SRAM (.srm): usually portable. Rename to match the new emulator's expected filename and it typically just works — same game, same region. This is how saves travel from phone emulators to desktop to flash carts.
  • Save states: never portable. Different cores, different versions, different emulators — states don't cross any of those lines. If you're switching emulators, load the old state in the old emulator, save in-game (SRAM), then move the SRAM file.
  • Memory cards: portable with care. Card images move between emulators that use the same format; .mcr is widely supported. Some emulators use proprietary card formats — convert via the old emulator first if needed.
  • Region matters. A US save won't load in the European version of the "same" game. Keep region-matched pairs.

08The backup routine (3-2-1)

Archivists swear by 3-2-1: three copies, on two different media, one off-site. For game saves that's gloriously cheap — saves are kilobytes:

  1. Copy 1: where the emulator keeps it (working copy).
  2. Copy 2: a saves-backup folder on your computer, synced after long sessions. Date it: saves-backup-2026-10-11.
  3. Copy 3: cloud storage or an external drive — the off-site copy that survives theft, spills, and dead laptops.

What goes in the folder: SRAM files, memory-card images, exported .state files, and a tiny text file noting which emulator version made them. Total size for a lifetime of retro saves: smaller than one phone photo. The only unforgivable data loss is the kind a five-minute copy would have prevented.
