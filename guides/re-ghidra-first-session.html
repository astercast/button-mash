Ghidra: your first session with a game binary

Ghidra is the free, open-source reverse-engineering suite the NSA released in 2019, and it is where most people first read the inside of a game: a real disassembler beside a real decompiler that reconstructs C-like code. This page gets you from install to a first honest hour with a binary you dumped yourself.

  • Free, scriptable, and genuinely good
  • ⏱ ~15 min
  • Intermediate
Legal lane: own your copy. Dump your own media, from hardware you own, with your own tools. Never download ROMs, ISOs, BIOS or firmware. Every project named here ships without the game; you feed it yours.

On this page

  1. What Ghidra is
  2. Install and make a project
  3. Let auto-analysis finish
  4. Read the two windows
  5. Rename as you learn

1. What Ghidra is

Ghidra (on GitHub at github.com/NationalSecurityAgency/ghidra, Apache-2.0) loads a compiled program, works out where its code and data live, and shows you both the machine instructions (the Listing) and a reconstruction of what those instructions mean in C-like pseudocode (the Decompiler). It handles the processors classic games were built on, MIPS for the N64 and PS2 era, PowerPC for GameCube, Wii and Xbox 360, ARM for handhelds, and plain x86 for PC games. Alternatives worth knowing by name: IDA Free (freeware, x86 and ARM), Binary Ninja (commercial, a modern API), and radare2 with its Cutter front end (open source, command-line first).

2. Install and make a project

Install a current Java runtime, download the Ghidra release, unzip it, and run ghidraRun. Create a new non-shared project and give it the game's name. Then import your file (File, Import File): your dumped executable or ROM image. Ghidra will guess the language and processor from the file; for game binaries the community around your specific system usually publishes the right loader settings, and one search with the console's name plus Ghidra loader is an evening well spent.

3. Let auto-analysis finish

On import, accept the auto-analysis offer and let it run to completion; on a game-sized binary this takes minutes, not seconds. Analysis finds functions, sorts code from data, and names what it recognises. Skipping it to peek early is the classic beginner mistake: everything downstream, including the decompiler's quality, stands on this pass.

4. Read the two windows

Work with the Listing and the Decompiler side by side. The Listing is the truth, instruction by instruction. The Decompiler is a reading of that truth in C-like code, variables named FUN_ and param_1 until you teach it better. Clicking a function in one window highlights it in the other. When the two disagree, the Listing wins. Start from strings: the Symbol Tree and the Defined Strings window list every scrap of text in the binary, menus, error messages, file names, and text is the friendliest map a beginner gets.

5. Rename as you learn

Reverse engineering in Ghidra is mostly naming. When you work out that a function draws the score, rename it (right-click, Rename) and its callers become clearer at once. Rename variables in the Decompiler the same way, add comments at the confusing parts, and bookmark the landmarks. An hour of honest renaming turns a wall of addresses into a program you can hold in your head, and it is exactly the daily work decompilation projects are made of.

6. Know what an evening can and cannot do

Extracting a texture or a sound to look at is an evening project. Understanding one subsystem, the save format, the level loader, is a satisfying month of evenings. Rebuilding a whole playable game is a community project measured in years, which is why the decompilation page exists and why using a finished port beats re-deriving one. Ghidra rewards the learner either way: you are reading the actual machine your childhood ran on.
