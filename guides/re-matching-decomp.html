Reverse engineering guide · Path B

Matching decompilation: rebuilding a game's source, byte for byte

A matching decompilation project rewrites a game's compiled code as human-readable C, checking every rewrite by compiling it and proving the output is identical to the original bytes. When one reaches 100 percent, the game exists as source code. This page explains how the trick works and how ordinary people contribute to it.

  • Years per game, and worth it
  • ⏱ ~14 min
  • Intermediate
Legal lane: own your copy. Dump your own media, from hardware you own, with your own tools. Never download ROMs, ISOs, BIOS or firmware. Every project named here ships without the game; you feed it yours.

1. What matching means

Take the game from a disc or cartridge a contributor owns. Disassemble it. Rewrite one function in C. Compile the rewrite with the project's pinned compiler. Then diff the compiled bytes against the original function's bytes. Identical means the rewrite is a true piece of the game's source; different means keep thinking. Multiply by every function in the game, across a community, over years. The repositories contain no game assets and cannot run without your original ROM or disc, which the build verifies by checksum.

2. The working loop, step by step

Clone the project for your game. Supply the exact original binary it names, version and region included, because US 1.0 and EU 1.1 are different programs. Build the toolchain the project pins. Pick a small unmatched function from the project's tracker. Rewrite it in C, guided by Ghidra. Compile, run the project's differ, and iterate until the bytes match exactly. Submit the function. That loop, repeated thousands of times by hundreds of people, is the entire method; the tooling around it, differ scripts, permuter tools that shuffle code arrangements hunting for a match, objdump for sanity checks, exists to make the loop faster.

3. Complete is not the same as playable

A project at 100 percent has the game's code as source. It does not automatically have a game you can play somewhere new: a port still needs a renderer, input handling and platform code written by someone. Some famous decompilations sat complete before their ports existed, and a few still wait. The reverse surprises people too: a partial decompilation, around 7 percent of Halo: Combat Evolved's code, already powered a playable derived port, because the missing 93 percent was not all load bearing. Percentage complete and playability are cousins, not twins.

4. Famous projects, as of October 2026

The Legend of Zelda: Ocarina of Time decompilation (the ZRET project) completed in November 2021 after about 21 months; its port, Ship of Harkinian, launched in March 2022 with widescreen and modern controllers, built and run with your own ROM. Majora's Mask has both a decompilation lineage and a recompiled port (see the recompilation page). Mario Kart 64's project carries a 100 percent badge, and Banjo-Kazooie's decompilation completed in 2024. On GameCube, Pikmin sits around 94 percent and Animal Crossing around 99 to 100 percent, with Metroid Prime early, around 17 percent. These figures drift monthly; the live census at decomp.dev is the authority, and this page is rechecked quarterly.

5. Picking your first function

Start where the community points newcomers: the project's issue tracker or Discord will name beginner-sized functions, often in menus or save handling rather than the rendering core. Match one small function exactly and you will understand the whole discipline better than a week of reading about it. And the honest alternative stands: if a finished port of your game exists, play it, and save your evenings. Reverse engineering your own copy for the learning is the hobby; re-deriving a solved game from zero is optional.
