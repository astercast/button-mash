Play together online: the netplay guide

Two couches, one game. How rewind-based rollback netplay puts a second player on your screen from across the internet — and the three rules that keep the session from falling apart.

  • Primary tool: RetroArch
  • ⏱ ~20 min
  • Intermediate
Legal lane: netplay syncs inputs, not games — every player still needs their own legal copy: a dump of a cartridge they own, or homebrew. Never send someone a ROM file to "get them set up."

01What netplay actually sends

Cloud gaming streams video to you; netplay does the opposite. Both players run the same emulator, the same core, the same game locally, and the network carries only controller inputs — a few bytes per frame saying "player 2 pressed right." Because both machines simulate the identical game from identical inputs, both screens agree. It's beautifully cheap: a dial-up-era idea that still beats video streaming on latency.

This is also why netplay can't conjure a game for someone who doesn't have it. If your friend hasn't loaded the same file on their own machine, there is nothing to sync. The legal lane and the technical lane are the same road here.

02How RetroArch's rollback works

Old netplay made everyone wait for the slowest player's inputs — fine on LAN, miserable on the internet. RetroArch's netplay is built on replay: your game runs ahead immediately with your own inputs (zero added input delay in the default configuration), and when the other player's inputs arrive late, the emulator rewinds to the last frame you both agreed on, replays with the real inputs, and lands on the corrected state — invisibly, in milliseconds.

Think of it as the emulator constantly re-doing the last few frames whenever new information arrives. As long as both sides agree on which frame is which, they can't drift apart: every input always lands on its correct frame. It supports up to 16 players plus spectators, which is why tournament streams and big co-op rooms use it.

Why this matters: rollback needs the emulator to snapshot and restore its entire state dozens of times per second. Cores that serialize state quickly give buttery netplay; cores that don't give slideshow netplay. That's the whole reason some systems work and others don't (section 5).

03The matching rule: same, same, same

RetroArch's own documentation states the guarantee plainly: netplay stays in sync only when the core is deterministic, the only inputs are gamepads/analog sticks, and both the core and the loaded content are identical on host and client. In practice, the pre-flight checklist is:

  • Same RetroArch version on every device (current stable is 1.22.2 as of late 2026).
  • Same core version — update cores on both sides before the session.
  • Byte-identical game content. Same dump, same file, same checksum. One byte of difference and the session desyncs — this is the #1 cause of "it worked yesterday."
  • No save states during the session. Loading a state mid-game is the #2 desync cause; the two machines' histories diverge permanently.

Cross-platform works — PC, Android, Steam Deck, and retro handhelds can share a session — with the caveat that wildly different CPU architectures can still behave differently at the margins. When in doubt, test a five-minute session before inviting the crowd.

04Hosting: lobby, relay, or port forward

One player hosts, the others join. The flow in RetroArch:

  1. Load the game on the host machine first.
  2. Open the Netplay menu → Start Netplay Host. The session appears in RetroArch's public lobby browser, or you share your IP directly.
  3. Clients use Connect to Netplay Host (or Refresh the lobby), join, and get assigned a controller port. The host is player 1 by default.

Two ways to cross the internet:

Relay servers (easiest)
RetroArch runs public relay servers (including locations in North America and Europe) that punch through NAT for you — zero router configuration. The cost is extra latency, since your inputs take a detour.
Port forwarding (fastest)
Forward TCP port 55435 on the host's router straight to the host machine. Lower latency, but you touch your router settings and your firewall must allow RetroArch.

Start with relay; switch to port forwarding if the delay bothers you. The official RetroArch netplay page and the libretro netplay docs document every setting.

05What plays well (and what doesn't)

Excellent: NES, SNES, Genesis, GBA, arcade (FBNeo)
Lightweight cores serialize fast, so rollback is invisible. This is the netplay sweet spot — 8-bit and 16-bit co-op and versus feel local.
Impractical: PlayStation, N64 and up
Heavier cores can't snapshot/restore fast enough for smooth rollback; sessions stutter or collapse. The docs are blunt: the performance requirements make the current model unsuitable for these.
Not emulated: link cables
RetroArch netplay syncs controllers, not link-cable data — so Game Boy link features like Pokémon trading don't work over netplay. Two exceptions: the TGB-Dual and SameBoy cores implement same-game GB/GBC multiplayer properly.

The Pokémon question, answered: no, you cannot trade Pokémon over RetroArch netplay. Link-cable emulation is a different technology from controller netplay. SameBoy's same-game multiplayer is the real answer for GB/GBC link play.

06New in 2026: Dolphin on your phone

Dolphin's 2609 release (September 2026) added Android NetPlay with lockstep networking against desktop clients — real cross-platform multiplayer between phones and PCs for GameCube and Wii games. It's lockstep rather than rollback (everyone waits for everyone, like the old days), which suits Dolphin's heavier cores, and it makes the phone in your pocket a legitimate netplay endpoint for the first time.

Dolphin is now also distributed directly through the Google Play Store, so the Android side of that equation is a normal app install. For GameCube/Wii multiplayer specifically, Dolphin — not RetroArch — is the current answer.

07Netplay on this site: the honest state

The EmulatorJS engine behind our Player advertises experimental WebRTC room-code netplay — but its own documentation flags it as still being worked on, and we have not verified it end-to-end on the stable build. So: not enabled here, not promised. We'd rather say "not yet" than ship a button that desyncs your game night.

What works today for playing together on Button Mash:

  • Hot-seat on one screen — the Player's controller remapping supports multiple gamepads on the same machine.
  • The Party Planner — builds a timed rotation across party-tagged games so a room full of people shares controllers fairly (plan a game night).
  • Tournaments — run a real bracket around whatever you're playing (bracket builder).

08Troubleshooting checklist

When a session misbehaves, walk this list in order — it resolves the vast majority of netplay grief:

  1. Desync right at the start: content mismatch. Compare checksums of the game file on both machines; re-copy the host's file to the client.
  2. Desync mid-session: someone loaded a save state, or core versions differ. Update cores everywhere, agree on no-states.
  3. "Failed to initialize netplay" as client: wrong IP, host hasn't started hosting yet, or the host's firewall is blocking RetroArch. Confirm the host's session is live first.
  4. Stutter that isn't desync: serialization too slow for the core (wrong system for netplay — see section 5), or relay latency. Try port forwarding; drop to an 8/16-bit game as a control test.
  5. One player's inputs feel delayed: that's the network, not the emulator — rollback hides it until latency gets extreme. Play closer (geographically) or accept it.
