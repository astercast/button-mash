Make games for dead consoles

The homebrew development primer: real toolchains, real hardware limits, and the honest path from "hello world" to a cartridge-worthy game, all with code and art you own.

  • Languages: C, some assembly
  • ⏱ ~25 min
  • Intermediate
Legal lane: homebrew means your game, your code, your art, your music. Never lift sprites, music, or code from commercial games. Build it from scratch and it's yours to share, sell, or press to a cartridge.

01Why dead consoles are the friendliest dev targets

Modern game development asks you to target a moving platform: new GPUs, new APIs, a store that takes a cut and a review queue. A 2001 handheld is the opposite. The Game Boy Advance has exactly one CPU (an ARM7TDMI at 16.78 MHz), exactly one screen (240×160), and exactly zero surprises. Every player on earth runs the identical hardware, so if it works on yours, it works on everyone's.

Constraints are a gift. A tiny screen and a fixed palette force you to design rather than decorate, and the feedback loop is minutes, not hours. The scene agrees: the GBA homebrew community ships new games every year, from jam entries to commercial-quality releases like the 2026 action roguelike Zombie Nest GBA. The MAGFest Indie Retro Homebrew Showcase's finalist lists read like a curriculum: NES, Game Boy, Genesis, even Dreamcast entries, all built by hobbyists.

The short version: if you can write basic C, you can ship a GBA game. The hardware is simpler than any phone, the tools are free, and the audience is real.

02Pick your first system (the honest ladder)

Not all retro hardware is equally welcoming. Ranked by how fast a beginner reaches something playable:

Game Boy Advance, start here
Programs in C with a real compiler, friendly libraries, the best tutorial ever written for any console (Tonc, below), and a forgiving CPU. The consensus first system.
Game Boy / Game Boy Color, the charming second
Simpler hardware than the GBA but a weirder CPU (the LR35902, a 6502/Z80 hybrid). You'll write more assembly-flavored code; the community at gbdev.io is the best-organized in retro dev.
NES, the rite of passage
6502 assembly or C with heavy constraints, plus the PPU's quirks (sprites, nametables, mappers). Rewarding, but expect your first month to be learning, not shipping.
SNES / Genesis / N64, later
Bigger chips, weirder buses, scarcer docs. Come back when you've shipped something small.

The rest of this guide walks the GBA path, with the 8-bit detour in section 5. Everything below assumes a Mac, Windows, or Linux computer, no special hardware needed to start.

03The GBA toolchain, end to end

The standard toolchain is devkitPro with its devkitARM package: a GCC cross-compiler targeting the GBA's ARM chip, plus libraries and examples. Install the devkitPro package manager for your OS (the graphical installer on Windows, the pkg on macOS, pacman-style on Linux), then pull the GBA packages:

sudo dkp-pacman -S gba-dev gba-examples

Then set three environment variables so your shell can find everything:

export DEVKITPRO=/opt/devkitpro
export DEVKITARM=${DEVKITPRO}/devkitARM
export PATH=${DEVKITPRO}/pacman/bin:${DEVKITPRO}/tools/bin:${DEVKITARM}/bin:$PATH

The fastest first project: copy the official template and build it.

cp -r /opt/devkitpro/examples/gba/template hello-world
cd hello-world
make

If that prints a .gba file with no errors, your toolchain works. The template is a minimal project: a Makefile in the root, C sources in source/, and an int main(void) entry point. You now own a build pipeline for a 2001 console. The whole setup is a one-evening job, and the same pattern (install manager, install <system>-dev, copy template, make) repeats for every devkitPro-supported system.

04Learn the hardware: Tonc and the 240×160 canvas

The single best resource in console homebrew is Tonc, a full GBA programming course that starts at "what is a register" and ends at mode-7-style affine backgrounds. Work through it in order; it's the rare tutorial that teaches the hardware, not just the library.

The mental model you need:

  • Modes: the GBA draws in numbered video modes. Mode 3 is a raw 240×160 bitmap (easy, slow); modes 0-2 are tile/sprite modes (fast, the real way games work).
  • Tiles & sprites: backgrounds are grids of 8×8 tiles; sprites (called "objects") are movable tiles with per-sprite priority, flipping, and palette selection. Learn these two and you can build most 2D games.
  • Palettes: 15-bit color (32 levels per channel). GBA art is drawn in tiny palettes, embrace it; it's the look.
  • Interrupts & timing: the vertical blank interrupt (60 times a second) is your heartbeat, update game logic there, draw between.

devkitPro ships two helper libraries: libgba (thin, official examples use it) and libtonc (the Tonc companion, better documented). Either works; beginners usually have a smoother time with libtonc. For a modern, higher-level engine, the community-built Butano engine wraps the hardware in clean C++, several released games were built on it.

05The 8-bit path: Game Boy and NES

If the Game Boy's green-tinted world calls to you, the toolchain is different but the spirit is the same:

  • RGBDS, the modern Game Boy assembler (writes the LR35902's dialect). The pro path; most serious GB homebrew uses it.
  • GBDK-2020, a C compiler for the Game Boy, maintained by the community. Write C, get a .gb out. The friendlier on-ramp.
  • gbdev.io, tutorials, the Pan Docs hardware reference, and the community hub. If Tonc is the GBA bible, Pan Docs is the GB one.
  • Homebrew Hub (hh.gbdev.io), the community's discovery index for finished games; study what shipped.

For the NES, the 6502 CPU is programmed with cc65 (C + assembler) or ca65 (pure assembly), and the community knowledge base is the long-running NES dev wiki. Expect mappers (cartridge bank-switching chips) to be your first real boss fight, start with mapper 0 (NROM, no bank switching) and simple games.

Scope discipline: the homebrew that ships is small. A one-screen arcade game, finished, beats a 40-hour RPG that dies in month three. Zombie Nest GBA is a 53 KB ROM, proof that tiny is a feature.

06Test like it's 2001

Develop on an emulator, validate on hardware. The emulator loop is seconds: build, drag the .gba into mGBA (mgba.io, current stable 0.10.5), see what broke. mGBA is accurate enough that emulator-tested code almost always behaves on real hardware, and its debugger (breakpoints, memory viewer) is better than anything that existed in 2001.

When the game is fun, run it on the real thing. Flash cartridges (EverDrive-style carts) load your .gba onto physical hardware, the ultimate compatibility test, and the way your game reaches players who own the console. Many homebrew releases ship exactly this way: a ROM on itch.io plus an optional physical cart run.

One honest warning: emulator bugs can mask hardware bugs. If something works in mGBA but glitches on a flash cart, the usual suspects are uninitialized memory (emulators zero it; hardware doesn't), timing assumptions, and DMA misuse. The Tonc chapters on each subsystem call these out, read them before you need them.

07Ship it: jams, itch.io, and showcases

Homebrew has a real distribution pipeline:

  • Game jams, the GBA Jam's 2026 entries page shows what a deadline produces; themed jams run year-round across systems.
  • itch.io, the home of homebrew distribution. Tag your page correctly (e.g. the Game Boy Advance tag), offer the ROM free or pay-what-you-want, and optionally a browser demo.
  • Showcases: MAGFest's annual Indie Retro Homebrew Showcase curates the year's best across NES, Game Boy, Genesis, and more. Finalists like Light From Within (NES) and NightVein (Genesis) started as somebody's evening project.
  • Physical releases, homebrew publishers press cartridges for standout games. Nothing says "shipped" like a box on a shelf.

Want to play other people's homebrew first? The homebrew & public-domain sources guide is the tasting menu, every game there is a study object with its authors' blessing.

08The legal lane for developers

Homebrew sits on the clean side of the line, and keeping it there is simple:

  • Your code, your art, your music. Write or commission everything. "Inspired by" is fine; copying sprites or ripping soundtracks is not.
  • Open-source the engine, keep the game yours, a common pattern: GPL the reusable bits, sell the game. Your call either way.
  • Clones are legal; copies aren't. You can make a game like a classic (mechanics aren't copyrightable); you can't ship its assets, name, or characters.
  • Fan games live in a gray zone. Using someone else's characters without permission can draw a takedown even when the work is free and loving. Original IP is the safe harbor.

The scene's rule of thumb: if every byte in the ROM is yours or licensed to you, you can sell it, share it, jam it, and press it, no lawyers required.
