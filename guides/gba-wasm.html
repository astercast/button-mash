How GBA becomes WebAssembly

A Game Boy Advance game is ARM machine code written for 2001 hardware. A browser speaks WebAssembly. The gap between them is one of the coolest reverse-engineering stories in emulation — here's how it works, in plain language.

1. The CPU problem: ARM in a browser

The GBA runs on an ARM7TDMI processor — a 32-bit RISC chip that understands two instruction sets: full 32-bit ARM instructions and compact 16-bit THUMB instructions, with the game switching between them constantly. Your browser's JavaScript engine can't run ARM code directly, and WebAssembly — the browser's near-native bytecode — is a completely different instruction set with its own rules.

Classic emulators solve this with an interpreter: a loop that reads one ARM instruction, figures out what it does, does it, and moves to the next. It works, but every game instruction costs dozens of host instructions to simulate. The recompiler pattern skips the middleman: translate the game's ARM code into WebAssembly once, ahead of time, then let the browser run the translation natively. The translated code runs at a large fraction of native speed because, well, it is native code by the time the browser's WASM engine compiles it.

2. Basic blocks: the unit of translation

You can't just transliterate instruction-by-instruction and call it a day — branches, condition flags, and the ARM/THUMB mode switch need care. The standard trick is to translate in basic blocks: straight-line runs of instructions that start at a label and end at the first branch.

Each block becomes one WASM function. Inside, ARM registers become WASM locals, and the ARM condition flags (negative, zero, carry, overflow) become explicitly tracked values. Branches between blocks become function calls or jumps in a dispatch loop. Self-modifying code — rare on GBA, but it exists — is handled by checksumming blocks and retranslating when a game writes over its own code.

The clever part: the translator doesn't need to understand what the game means. It's a mechanical mapping — "this ARM add-with-carry becomes these WASM integer ops" — applied millions of times. Dumb, fast, and correct is the whole philosophy.

3. Memory mapping: faking the hardware

A GBA game doesn't just compute — it constantly pokes hardware. Writing to one memory address draws sprites; reading another returns button states; a third region is the 96KB of video RAM. The GBA's address space is a patchwork of real RAM, ROM, and memory-mapped I/O registers that stand in for physical chips: the picture processing unit, four sound channels, DMA controllers, timers, the serial port.

A browser WASM module gets one flat block of linear memory, so the runtime builds a memory map on top of it: reads and writes to hardware addresses are intercepted and routed to JavaScript or WASM implementations of each chip. The PPU implementation rasterizes backgrounds and sprites scanline by scanline; the audio code synthesizes the GBA's distinctive square-wave channels into Web Audio buffers. To the translated game code, it feels exactly like real hardware. That's the whole trick of emulation: a convincing forgery at the boundary between software and silicon.

One more piece: the BIOS. Real GBA games call into Nintendo's built-in firmware for math routines and decompression. Recompiler projects reimplement those calls from scratch (clean-room HLE — high-level emulation) so no copyrighted firmware is needed.

4. Frame timing: 59.73 frames per second

The GBA doesn't run "as fast as possible" — it runs at exactly 59.73 frames per second, because its video hardware draws 228 scanlines per frame at a fixed pixel clock. Games depend on this rhythm: music tempo, animation speed, even random-number generators assume the timing.

In a browser, the display refreshes on its own schedule (usually 60Hz, sometimes 120Hz+), so the runtime has to pace the translated code: run one frame's worth of emulated cycles, then wait for the right moment before the next. Too fast and the game runs like it's on fast-forward; too slow and audio crackles as the sound buffer starves. The standard solution is a scheduler driven by requestAnimationFrame with an audio clock as the ground truth — if the sound is smooth, the timing is right.

5. Trust but verify: differential testing

Here's the hard question: how do you know the translation is correct? A single mistranslated flag can corrupt a game hours in. The serious projects answer with differential verification: run the same game code through both the WASM translation and a trusted interpreter, and compare the CPU state after every block. Any divergence is a translation bug, caught immediately and automatically.

This is what makes the experimental hybrid recompilers credible despite their complexity — the interpreter is the oracle, the recompiler is the student, and the test harness never lets the student graduate with a wrong answer. Reports from these projects put ~99.8%+ of executed instructions on the native-WASM path, with the interpreter only handling the exotic leftovers.

6. What breaks, and why

  • Anti-piracy checks — some games probe hardware quirks that a recompiler's memory map doesn't reproduce exactly. The fix is usually a better hardware model, not a better translator.
  • Timing-sensitive tricks — games that race the video beam or abuse DMA timing expose every pacing flaw. These are the last 1% of compatibility.
  • Save types — GBA carts used SRAM, Flash, and EEPROM chips; the runtime must detect and persist each type (usually via IndexedDB) or saves vanish.
  • Link cable — multiplayer over the GBA link port needs networking (WebRTC data channels in browser builds) and cycle-tight synchronization between two instances.
